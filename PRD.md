# PRD: Keitaro Wrapper

Версия: 1.0 · Дата: 2026-11-17

## 1. Цель

Сделать обёртку над рекламным трекером Keitaro, которая решает две задачи:

1. **Создатель кампаний** — за одно действие создаёт в Keitaro кампанию с корректно
   настроенными доменом, группой, источником и двумя потоками.
2. **Редактор кампании** — позволяет управлять офферами в потоках существующей
   кампании: добавлять, удалять, возвращать, закреплять веса, публиковать и отменять
   изменения.

Keitaro остаётся источником истины для опубликованного состояния. Обёртка хранит
локальное представление кампании, черновик изменений и архив удалённых офферов.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Кампания | Сущность Keitaro (`/campaigns`), содержит потоки |
| Поток / flow / stream | Правило распределения трафика внутри кампании |
| Оффер | Партнёрская страница, на которую уходит трафик |
| Share / вес | Доля трафика оффера в потоке, целое число процентов |
| Pinned | Локальный флаг «закрепить вес»: операции не меняют долю оффера |
| Draft / dirty | Локальные неопубликованные изменения потока |
| Snapshot | Снимок состояния офферов на момент последнего fetch/push |
| Removed / archived | Оффер удалён из потока, но остаётся в локальном архиве |

## 3. Пользовательские сценарии

1. Пользователь заполняет форму: название, гео, оффер, домен, группа, источник.
   Обёртка создаёт кампанию с двумя потоками и открывает её редактор.
2. Пользователь открывает редактируемый поток, добавляет оффер через автокомплит.
   Веса пересчитываются, таблица становится жёлтой (есть неопубликованные изменения).
3. Пользователь нажимает `Push` — список активных офферов и веса уходят в Keitaro,
   жёлтая подсветка исчезает.
4. Пользователь нажимает `Cancel` — черновик откатывается к последнему
   опубликованному/загруженному состоянию.
5. Пользователь удаляет оффер — строка сереет, вес становится 0%, поток становится
   dirty. После `Push` оффер исчезает из Keitaro, но остаётся в архиве обёртки.
6. Пользователь нажимает `Bring back` — оффер возвращается в поток, веса
   пересчитываются, поток снова dirty (если удаление уже было опубликовано).
7. Пользователь удалил оффер напрямую в Keitaro и нажал `Fetch streams` — оффер
   остаётся в обёртке серым (`removed`), доступен `Bring back`.
8. Пользователь закрепляет вес оффера (`Pin`) — последующие добавления/удаления
   пересчитывают веса всех офферов, кроме pinned.

## 4. Функциональные требования

### 4.1. Создатель кампаний

**Входные данные**

| Поле | Тип | Обязательное | Примечание |
| --- | --- | --- | --- |
| Название кампании | строка | да | должно быть уникальным в Keitaro |
| Гео-код страны | 2 латинские буквы | да | приводится к верхнему регистру |
| ID оффера | целое | да | выбирается через автокомплит |
| Домен | ID из `/domains` | да | выпадающий список |
| Группа | ID из `/groups?type=campaigns` | да | выпадающий список |
| Источник трафика | ID из `/traffic_sources` | да | выпадающий список |

**Алгоритм**

1. Провалидировать гео (`^[A-Z]{2}$` после `upper()`).
2. Проверить существование оффера (`GET /offers/{id}`) и выбранных домена, группы,
   источника (списки из API).
3. Создать кампанию:
   ```json
   POST /campaigns
   {
     "name": "<название>",
     "alias": "<slug>-<6 hex>",
     "type": "position",
     "domain_id": 1813,
     "group_id": 10332,
     "traffic_source_id": 836
   }
   ```
   Alias: латиница/цифры из названия через дефис; если ничего не осталось —
   `campaign`; суффикс из 6 hex-символов гарантирует уникальность.
4. Создать Flow 1:
   ```json
   POST /streams
   {
     "campaign_id": 212860,
     "type": "regular",
     "name": "Geo DE -> Google",
     "position": 1,
     "schema": "redirect",
     "action_type": "http",
     "action_payload": "https://google.com",
     "filters": [{"name": "country", "mode": "accept", "payload": ["DE"]}],
     "collect_clicks": true,
     "offers": [],
     "landings": [],
     "triggers": []
   }
   ```
5. Создать Flow 2:
   ```json
   POST /streams
   {
     "campaign_id": 212860,
     "type": "regular",
     "name": "Offers",
     "position": 2,
     "schema": "landings",
     "action_type": "http",
     "action_payload": "",
     "collect_clicks": true,
     "offers": [{"offer_id": 24800, "share": 100, "state": "active"}],
     "landings": [],
     "triggers": []
   }
   ```
   Фильтров у Flow 2 нет — он ловит весь трафик, который не поймал Flow 1.
6. Если создание любого потока завершилось ошибкой — архивировать созданную кампанию
   (`DELETE /campaigns/{id}`), чтобы повторная попытка не упиралась в занятое имя.
7. Сохранить кампанию, оба потока и оффер (share = 100) в локальную БД. Snapshot =
   текущее состояние. Вернуть карточку кампании.

**Критерии приёмки**

- В Keitaro появилась кампания с выбранными domain_id, group_id, traffic_source_id.
- У кампании ровно два потока: geo-редирект на Google и поток с оффером.
- Flow 1 содержит country-фильтр с выбранным гео и `action_payload=https://google.com`.
- Flow 2 содержит выбранный оффер со 100% веса.
- Локальная БД содержит эту кампанию и оба потока.

### 4.2. Редактор кампании

**Отображение**

- Список потоков кампании, упорядоченный по `position`.
- Для каждого потока: номер, название, статус.
- Потоки, у которых схема не `landings` (например, geo-редирект), показываются
  read-only: название и пометка «redirect flow». Их фильтры, URL и прочие настройки
  не парсятся и не редактируются.
- Потоки со схемой `landings` отображают таблицу офферов:
  - колонки: Offer, Share, Pin, Actions;
  - активные офферы — обычные строки;
  - удалённые — серый текст, зачёркнутое имя, пометка `(removed)`, 0%, кнопка
    `Bring back`;
  - внизу — поле автокомплита и кнопка `Add`.
- Кнопки `Push` и `Cancel` видны, когда у потока есть неопубликованные изменения.
- При наличии draft таблица офферов имеет бледно-жёлтый фон, у потока — бейдж
  `unpublished changes`.

**Добавление оффера**

- Автокомплит ищет по ID и имени через `GET /api/offers?q=`.
- Выбранный оффер показывается в поле целиком; затем нажимается `Add`.
- Сервер проверяет оффер в Keitaro (`GET /offers/{id}`).
- Если оффер уже активен — 400.
- Если оффер есть в архиве — он возвращается в поток (не дублируется).
- После добавления пересчитываются веса, поток становится dirty.

**Удаление оффера**

- Оффер помечается `removed`, его вес = 0, pin снимается.
- Веса оставшихся активных офферов пересчитываются.
- Поток становится dirty. В Keitaro ничего не меняется до `Push`.
- Локальная запись не удаляется — это архив для `Bring back`.

**Возврат оффера**

- `removed` снимается, оффер снова участвует в распределении весов.
- Поток становится dirty: если удаление уже было опубликовано, возврат нужно
  опубликовать; если нет — оффер просто снова становится активным в черновике.

**Pin**

- Закрепляет текущий вес оффера.
- Pin — локальный флаг, в Keitaro не отправляется.
- Сам pin не меняет веса и не делает поток dirty.
- Все последующие add/remove/restore пересчитывают только незакреплённые офферы.
- Удалённый оффер закрепить нельзя; при удалении pin снимается.

**Push**

1. Собрать активные офферы (`removed = false`).
2. `PUT /streams/{keitaro_id}` с полным списком активных офферов:
   ```json
   {"offers": [{"offer_id": 10184, "share": 50, "state": "active"}]}
   ```
   Keitaro заменяет список офферов потока переданным.
3. Обновить локальные веса из ответа, сохранить snapshot, снять dirty.

**Cancel**

- Восстанавливает состояние офферов из snapshot: удаляет офферы, добавленные после
  последнего fetch/push, возвращает удалённые и их веса, восстанавливает pin.
- Снимает dirty. В Keitaro запросов не делает.

**Fetch streams**

- `GET /campaigns/{keitaro_id}/streams`.
- Для каждого потока обновляются name/position/schema/action/filters.
- Офферы из Keitaro становятся активными с весами из API.
- Новые для обёртки офферы добавляются (имя запрашивается через `GET /offers/{id}`,
  при ошибке используется ID).
- Локальные офферы, которых нет в Keitaro, помечаются `removed` и получают 0%.
- Snapshot обновляется, dirty снимается. Незапубликованный черновик при этом
  отбрасывается (источник истины — Keitaro). Pin-флаги сохраняются.

### 4.3. Пересчёт весов

Правила:

1. Участвуют только активные офферы (`removed = false`).
2. Pinned-офферы сохраняют свой вес.
3. Остаток `100 - сумма(pinned)` делится поровну между незакреплёнными.
4. Остаток от деления (1% на оффер) достаётся первым офферам в порядке вставки.
5. Удалённые офферы всегда получают 0%.
6. Сумма весов активных офферов всегда равна 100 (если есть хотя бы один активный
   и pinned-веса не заняли все 100).

Псевдокод:

```python
active = [o for o in offers if not o.removed]
pinned = [o for o in active if o.pinned]
others = [o for o in active if not o.pinned]
remaining = max(0, 100 - sum(o.share for o in pinned))
base, extra = divmod(remaining, len(others)) if others else (0, 0)
for i, o in enumerate(others):
    o.share = base + (1 if i < extra else 0)
for o in offers:
    if o.removed:
        o.share = 0
```

Примеры:

| Ситуация | Веса |
| --- | --- |
| 3 оффера | 34 / 33 / 33 |
| 4 оффера | 25 / 25 / 25 / 25 |
| 4 оффера, первый pinned (25), второй удалён | 25 / 0 / 38 / 37 |
| 2 pinned (40, 60) + 1 обычный | 40 / 60 / 0 |
| 2 оффера, второй удалён | 100 / 0 |

### 4.4. Импорт существующей кампании

`POST /api/campaigns/import` с `keitaro_id`:

- если кампании нет локально — `GET /campaigns/{id}`, создать локальную запись
  (domain/group берутся из ответа), затем выполнить Fetch-синхронизацию;
- если уже есть — просто синхронизировать.

## 5. Архитектура

```
React (Vite)  ──/api──▶  FastAPI  ──httpx──▶  Keitaro Admin API
                            │
                            └── SQLAlchemy ──▶ SQLite (keitaro.db)
```

- Backend синхронный: FastAPI-эндпоинты и `httpx.Client`.
- Ошибки Keitaro (`4xx/5xx`) транслируются как HTTP 502 с оригинальным `detail`.
- Транспортные ошибки повторяются до 3 раз с паузой 0.5 / 1 с.
- Собранный фронтенд раздаётся FastAPI через `StaticFiles`; в dev-режиме Vite
  проксирует `/api`.

## 8. Интеграция с Keitaro

База: `https://tlgk.host/admin_api/v1`, заголовок `Api-Key`. Ключ и базовый URL
берутся из окружения; ключ хранится только в `backend/.env` (gitignored), шаблон —
`backend/.env.example`. Без ключа приложение не стартует.

Используемые методы:

- `GET /campaigns/{id}` — импорт;
- `POST /campaigns` — создание;
- `DELETE /campaigns/{id}` — откат при неудачном создании потоков;
- `GET /campaigns/{id}/streams` — fetch;
- `POST /streams` — создание потоков;
- `PUT /streams/{id}` — публикация офферов;
- `GET /offers`, `GET /offers/{id}` — поиск и валидация офферов;
- `GET /domains`, `GET /groups?type=campaigns`, `GET /traffic_sources` — метаданные.

Особенности API, учтённые в реализации:

- `PUT /streams/{id}` с массивом `offers` **заменяет** список офферов потока;
  чтобы удалить оффер, достаточно не передавать его.
- `share` — целое число; сумма должна быть 100.
- Параметр `search` у `/offers` фактически игнорируется сервером, поэтому поиск
  выполняется по полному списку офферов на стороне backend.
- Название кампании должно быть уникальным; ошибка Keitaro возвращается
  пользователю как есть.

## 9. Обработка ошибок и крайние случаи

| Ситуация | Поведение |
| --- | --- |
| Неверный гео-код | 400, сообщение пользователю |
| Неизвестный домен/группа/источник | 400 |
| Неизвестный оффер | 502 с ошибкой Keitaro |
| Дубликат названия кампании | 502, текст Keitaro в UI |
| Ошибка создания потока | кампания архивируется, ошибка возвращается |
| Сетевой сбой Keitaro | до 3 попыток, затем 502 |
| Добавление уже активного оффера | 400 |
| Pin/удаление удалённого оффера | 404 |
| Нет активных офферов | Push отправляет пустой список, все остаются в архиве |
| Pinned-офферы занимают 100% | остальные получают 0% |
| Fetch при наличии черновика | черновик отбрасывается, состояние берётся из Keitaro |
| Оффер удалён в Keitaro | при fetch становится `removed`, доступен Bring back |
| Оффер восстановлен в Keitaro | при fetch снова становится активным |

## 10. Тестирование

1. `backend/check_weights.py` — 5 assert-кейсов на алгоритм весов (запуск:
   `uv run python check_weights.py`).
2. End-to-end проверка на живом Keitaro:
   - создание кампании: 2 потока, гео-фильтр, редирект, домен/группа/источник;
   - добавление офферов: 2 → 50/50, 3 → 34/33/33, 4 → 25×4;
   - pin 25 + удаление → 25/38/37;
   - Cancel возвращает snapshot и удаляет черновые офферы;
   - Push: список в Keitaro совпадает с локальным;
   - внешнее удаление оффера в Keitaro → Fetch → оффер `removed` → Bring back → Push;
   - все проверки прошли.

## 11. Границы scope

Входит: создатель кампаний, редактор офферов, import, fetch-синхронизация, веса, pin,
push/cancel, локальный архив.

Не входит:

- авторизация и мультипользовательский режим;
- статистика, тренды, клики (колонки Stats/Trends из примера UI);
- редактирование фильтров, редирект-URL и прочих настроек потоков;
- создание/редактирование офферов и кампаний вне описанных сценариев;
- массовые операции и пагинация больших списков;
- удаление кампаний из UI.
